# 01 — Architecture principles

Status: principles applied to the Phase 01 implementation; see the feature documentation for actual file ownership and verification limitations. Read [AGENTS.md](../AGENTS.md) for boundaries and strict WPF rules; [Project Rules](00.Project-Rules.md) controls naming.

- **Maintainability:** choose simple, focused files and descriptive names. Explain why an architectural boundary exists in plain language. Avoid speculative layers, giant files, and duplicate implementations.
- **Separation of responsibilities:** views handle presentation; view models handle presentation state/actions; approved domain behavior stays independent of UI details. Use MVVM where it simplifies binding and testing, not as a reason to add a framework or wrapper for everything. Phase 01 uses native INotifyPropertyChanged, IDataErrorInfo and ICommand without an MVVM package.
- **Dependency minimization:** prefer verified native WPF/.NET capabilities. Justify any new dependency by concrete need, compatibility, licensing, maintenance, and user approval. Existing package references are not automatically approved.
- **Resource management:** centralize theme resources and semantic keys, document dictionary ownership/load order, avoid duplicate keys, dispose owned resources, and unsubscribe long-lived event subscriptions where necessary. Keep UI changes on the appropriate dispatcher; avoid blocking the UI thread.
- **Logging and failure handling:** provide understandable failures and useful diagnostic context without credentials or sensitive user data. Do not swallow failures or add logging infrastructure before it is needed and approved. Logging backend, levels, retention, and location are open decisions.
- **Testing:** test meaningful state transitions, commands, token/appearance selection, and regressions; separate non-UI logic tests from Windows-only WPF checks. Tests complement compilation and real-screen inspection, never replace them.
- **Accessibility:** support keyboard operation, visible focus, meaningful labels/automation names, readable text, contrast, and non-color status cues. Consider system high-contrast and reduced-motion preferences; decorative depth must not carry essential meaning alone.
- **Performance:** reuse resources and styles, limit expensive effects and repeated allocations, avoid unnecessary layout work, and virtualize larger collections if they are later approved. Measure actual preview behavior before optimization; no responsiveness claims without evidence.

## Approved theme architecture requirements

The [permanent isolation rules](../AGENTS.md) and [exact naming tree](00.Project-Rules.md) govern ownership. The shared engine is **non-visual infrastructure only**. It registers theme metadata/factories, selects theme/mode, validates independent candidate packages, replaces/unloads the active resource slot and notifies consumers. It has no XAML, palette, default component visuals, persistent global style dictionary, Bento switch statements or cross-theme fallbacks.

Each individual theme owns a complete visual implementation: both token/brush dictionaries, all component styles/templates, typography/spacing/shape/depth/state treatments, documentation and validation expectations. Shared component contracts define semantic resource roles and necessary WPF target types; they never force unrelated themes to implement Bento’s look. Application screens consume active resources; no duplicated screens or executables per theme.

Bento’s factory (`Theme/ThemeBento/step1.e.7.BentoResources.cs`) composes its own appearance values with its own component files. It retains sealed style objects **inside Bento only** to preserve template/control identity across modes, but returns fresh dictionaries and brushes on each load. No caller can remove a style key from another candidate or damage the active set through a shared mutable dictionary. Another theme owns its own composition strategy; none is installed or simulated now.

ThemeService validates the complete candidate (102 semantic roles and 47 required style targets), rejects duplicate keys across its merged tree, then replaces **one entire package** without clearing unrelated application resources. It does not retain Bento visual dictionaries when switching identity. Lookup for validation never falls back to Application.Current resources. Loading/type/key failures retain the prior package/state with contextual diagnostics; an activation exception attempts to restore the previous slot and is rethrown. Runtime failure/recovery remains subject to actual Windows checks, not presumed transaction guarantees for arbitrary consumer code.

All mutable visual references use DynamicResource. Bento’s invariant inheritance/helpers use StaticResource only within their own file, avoiding sibling merge-order dependency. Do not borrow resources from another theme, cache brushes in views, or silently override duplicate keys. Existing windows, dialogs, popups, editing state and bindings must survive mode changes predictably. No further theme until Bento review/correction/approval.

## Windows verification architecture

[windows-wpf.yml](../cols/ci/windows-wpf.yml) runs on windows-2022, installs official .NET 8 SDK, restores/builds actual product and test projects, runs portable checks/regressions, compiled contracts and STA runtime smoke. Project commands deliberately avoid SDK 8’s lack of .slnx support; target net8.0-windows7.0 is unchanged. Native failures/timeouts fail the job. No release/artifact upload is configured.

Do not install SDKs/runtimes locally here. The workflow remains intentionally inactive in cols/ci and has not run; no Windows compilation or native result is implied by a push. See the current [isolation/CI evidence](../step1.ThemeStudio/step1.c.docs/step1.c.3.Theme-Isolation-and-CI.md). A successful future CI build will prove compilation only; the STA harness provides limited real-WPF runtime assertions with software rendering, not visual approval, physical DPI checks or performance certification.

## Research/approval still required

- Root integration was explicitly authorized. Unrelated module files remain excluded and untouched; any future modification/deletion outside Phase 01 still requires authorization. No parallel app directory.
- Phase 01 retains the root net8.0-windows7.0 WPF project and adds only the approved LiveChartsCore.SkiaSharpView.WPF 2.0.4 chart dependency; SDK pinning/future target upgrades, deployment and supported production OS policy remain future decisions, not implied Windows 7 support.
- MVVM implementation choice, any dependency injection/logging packages, testing tools, packaging and deployment.
- One complete theme-package slot is replaced only after token/style/duplicate-key validation; no global visual styles remain installed independently. Native opaque surfaces/edges provide elevation without blur or shadow effects. Runtime replacement still requires Windows verification.
- Measurable performance budgets, supported DPI/window sizes, typography/font licensing, high-contrast and reduced-motion behavior.

These are open questions, not authorization to introduce infrastructure, databases, or future modules. Record approved answers in the [decision log](05.Decision-Log.md).

## Approved chart boundary

The [analytics guide](../Theme/step1.f.Analytics/step1.f.6.Analytics-README.md) records dependency evaluation and the typed immutable interface. Shared controls adapt their theme dependency properties into library paints; no resource lookup, demo data, business totals or palette enters the renderer. Bento owns complete chart/table/KPI visuals. This is one package for actual plotting, not a custom engine or a browser substitute.
